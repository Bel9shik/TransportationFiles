# Исправление скорости передачи, 2–3 ноября 2026

Текущий статус: основной провал устранён на Mac и Linux. На Windows последний
полный CI всё ещё показывает 7,8% отставания на 100 МиБ (0,601 / 0,557 с),
хотя другие контролируемые серии быстрее Java; точный паритет не объявляется.
Отдельный повторный запуск macOS Intel остаётся нестабильным. PR — черновик.
Ниже сохранены успешные, неудачные и отклонённые измерения с исходными JSON.

На Mac M4 Pro / 48 ГиБ / macOS 26.6.2 регрессия передачи устранена в повторных
AOT-замерах. Условия совпадают с [первым сравнением](../2026-10-31/README.md):
Java 17.0.17, Dart 3.13.7, отдельные процессы, localhost, реальные gRPC-ядра,
запись файлов и проверка SHA-256, три прогрева и семь измерений.

| Нагрузка | Java, медиана | Исправленный Dart AOT, медиана | Java / Dart, МиБ/с |
|---|---:|---:|---:|
| 1 × 100 МиБ | 0,4439 с | 0,1578 с | 225,28 / 633,90 |
| 20 × 1 МиБ | 0,0872 с | 0,0305 с | 229,46 / 656,66 |

Дополнительно измерены смешанные пары: на 100 МиБ Java → Dart — 0,323 с,
Dart → Java — 0,487 с. Это проверяет производительность совместимости со старой версией.
Все 840 полученных файлов, включая прогревочные, независимо сверены Python по
размеру и SHA-256. [Сырые результаты](transfer-macos-arm64.json).
При первой передаче в этой серии 100 МиБ заняли 0,187 с у Dart и 0,609 с у Java.
Сервер теперь проверяет нативный SHA-256 перед открытием порта: загрузка библиотеки
относится к подготовке сервера, которая в обоих приложениях происходит до начала
этого таймера. В UI подготовка запускается после первого кадра; данные файла заранее
не читаются и не хешируются.
Холодный старт, физическая сеть и влияние VPN этим тестом не измеряются.

## Причина и исправление

До изменений [короткое повторение](diagnostic-before.json) подтвердило 6,697 с у
Dart против 0,464 с у Java на 100 МиБ. Самостоятельные AOT-пробы показали около
0,42 с на SHA-256, 0,01 с на protobuf encode/decode и 0,04 с на запись 100 МиБ.
CPU-профиль JIT использовался только для локализации, не для численного сравнения AOT.

Основной провал — обратная связь управления потоком http2 2.3.1. Получатель
отправлял WINDOW_UPDATE на каждый фрагмент, а отправитель расходовал даже крошечный
кредит немедленно. Размер сообщения с 64-КиБ содержимым превышал 65535-байтное окно,
и передача дробилась всё сильнее. На одном диагностическом прогоне после увеличения
окна потока было 46 294 DATA-фрейма по 71 байту, помимо других мелких фрагментов.

Теперь окно потока составляет 1 МиБ, окно соединения — 4 МиБ, а максимальный
HTTP/2 DATA-фрейм — 128 КиБ: 64-КиБ содержимое с заголовками помещается в один кадр. Подтверждения объединяются до 16 КиБ на поток/соединение. Остаток отправляется в следующем обороте цикла событий или перед другими
исходящими кадрами, без искусственной миллисекундной задержки. Порядок управляющих кадров, полный объём кредитов, обратное
давление сокета, ограничение входящего gRPC-сообщения и отмена сохранены.
Тест с 1000 маленькими подтверждениями воспроизвёл проблему до исправления.
Синхронные исходящие HTTP/2 фреймы также собираются в socket-записи с порогом 64 КиБ
с выдачей остатка в следующей микрозадаче. На Windows порог — 1 МиБ, остаток
отправляется в следующем обороте цикла событий: это объединяет также gRPC-микрозадачи
и уменьшает число системных записей. На Mac такая настройка ухудшила результат,
поэтому там и на остальных платформах сохранён исходный режим 64 КиБ. Запись на диск и хеширование получателя
группируются в ограниченные порции до 1 МиБ плюс один сетевой блок. Хеширование
буфера выполняется одновременно с ожидающей асинхронной записью; перед дальнейшей
обработкой ожидаются обе операции; сетевой блок
остаётся не больше 64 КиБ. Отправитель также читает и хеширует порции по 1 МиБ,
отправляя их 64-КиБ сообщениями с проверкой отмены между сообщениями.

После этого ограничением стало хеширование. SHA-256 перенесён на потоковый
[webcrypto/BoringSSL](https://pub.dev/packages/webcrypto), с одним блоком в обработке
и массовым копированием типизированных байтов. Адаптер публичного List/Iterable API
устраняет побайтовый обход skip/take перед передачей в нативную библиотеку.
Проверка не отключалась и алгоритм не менялся.

Окно соединения — отдельная настройка: одного увеличения окна потока оказалось
недостаточно на Linux и Windows. В `http2` 2.3.1 оно было фиксировано на 65535
байтах, поэтому подключено [upstream-исправление](https://github.com/dart-lang/http/commit/23f8574cdfce93c3bb0c6d83d92167d92b9824d5)
с настройкой окна. `grpc` 5.2 пока ограничивает зависимость версией 2.x, поэтому
используется явный `dependency_overrides` и тестируется совместимость протокола.

`webcrypto` 0.6.1 не включал четыре fiat ADX assembly-файла в Apple x64 сборку.
Закреплена ревизия [исправления #448](https://github.com/google/webcrypto.dart/pull/448)
`e50fcce3d0c30627b11ffc74eb964b1073d42620`. Обе Git-зависимости закреплены по SHA;
после официальных выпусков с этими исправлениями нужно вернуться на pub-версии.
Для Android native hooks закреплён NDK 28.2.13676358, как у Flutter: иначе CI
может выбрать установленный старый NDK и получить ELF-сегменты с выравниванием 4 КиБ.

Дополнительный остаток задержки на Windows объяснялся различием сохранения:
Dart вызывал `RandomAccessFile.flush` (принудительный физический сброс), а Java
закрывала файл без `fsync`/`force`. Раздельные AOT-пробы в CI показали
[0,53–0,65 с на flush 100 МиБ в Windows](components-windows-before-close.json) и
[0,35–0,43 с на Linux](components-linux-before-close.json), отдельно от записи.
Теперь обе реализации ждут записи и закрытия файла перед публикацией; SHA-256,
проверка размера и сохранение без перезаписи остаются. Подтверждение означает
готовый файл в файловой системе; отдельная гарантия сброса на физический носитель
при потере питания не предоставляется, как и в исходной Java-версии.

## Ограничение очереди отправителя

В grpc-dart 5.2 оба участка отправки используют `listen(sink.add)`, поэтому пауза
HTTP/2 не возвращается к генератору файлов. Java ожидает `isReady()` перед блоком.
Новый мост передаёт DATA через публичный `StreamSink.addStream`, а генератор
резервирует место до сериализации каждого сообщения, включая финальный SHA-256.
Лимит — 16 сообщений (около 1 МиБ содержимого) плюс текущий 1-МиБ буфер чтения;
при отмене, reset и завершении RPC ожидающий генератор освобождается. Параллельные
отправки одним экземпляром `TransferSender` явно отклоняются; отдельные экземпляры
независимы.

Повтор на одном Mac M4 Pro, три прогрева + семь измерений на сценарий и смешанную
пару, проверка всех 2520 сохранённых файлов в трёх сериях:

| Режим | Dart, 100 МиБ | Java, 100 МиБ | Dart, 20 × 1 МиБ |
|---|---:|---:|---:|
| Контроль до | 0,1495 с | 0,4325 с | 0,0297 с |
| Очередь до 16 сообщений | 0,1266 с | 0,4107 с | 0,0285 с |
| Контроль после | 0,1444 с | 0,4110 с | 0,0270 с |

[Контроль до](macos-upload-backpressure/before.json),
[новый мост](macos-upload-backpressure/after.json),
[контроль после](macos-upload-backpressure/control-last.json).
100-МиБ передача ускорилась относительно обоих контролей; разница малых файлов
сопоставима с колебаниями контроля.

[На Windows](https://github.com/Bel9shik/TransportationFiles/actions/runs/41582306445)
проведено три прогрева и девять измерений с контролем до и после:

| Режим | Dart, 100 МиБ | Java, 100 МиБ | Dart, 20 × 1 МиБ |
|---|---:|---:|---:|
| Контроль до | 0,7679 с | 0,9368 с | 0,1559 с |
| Очередь до 16 сообщений | 0,6431 с | 0,4909 с | 0,1394 с |
| Очередь до 64 сообщений | 0,6801 с | 0,4974 с | 0,1448 с |
| Контроль после | 0,7550 с | 0,4927 с | 0,1487 с |

[Сырые данные](windows-upload-backpressure/). Java в первом контроле нестабильна;
её замедление нельзя считать победой Dart. Лимит 16 ускоряет Dart примерно на 15%

Порог CI 1,20 оставлен без изменений; одного ограничения очереди недостаточно.

## Подготовка исходного файла на Windows

Следующее исправление выносит чтение 1-МиБ порций и их SHA-256 в один фоновый
isolate на отправителя. Он переиспользуется между файлами и отправками; основному
isolate передаются типизированные байты через `TransferableTypedData`.
Одновременно готовится только один следующий блок, файл читается и хешируется
за один проход. 64-КиБ сообщения, лимит очереди и протокол не меняются.
При отмене ожидается текущая операция, закрывается файловый дескриптор, а при
закрытии отправителя — и сам worker. Остальные платформы сохраняют прежний путь.
[Windows AOT-сравнение](https://github.com/Bel9shik/TransportationFiles/actions/runs/41585029325),
три прогрева + девять измерений и контроль до/после:

| Режим | Dart, 100 МиБ | Java, 100 МиБ | Dart → Java, 100 МиБ | Dart, 20 × 1 МиБ |
|---|---:|---:|---:|---:|
| Только лимит очереди, до | 0,5184 с | 0,5762 с | 0,7021 с | 0,1094 с |
| Лимит + фоновая подготовка всех файлов | 0,5097 с | 0,5583 с | 0,6428 с | 0,1141 с |
| Только лимит очереди, после | 0,5170 с | 0,5611 с | 0,7077 с | 0,1095 с |

[Сырые данные](windows-prepared-source/). Все 3024 полученных файла проверены
независимо по размеру и SHA-256. На этой машине Dart быстрее Java и без worker;
различие с предыдущим runner показывает, почему одного успешного прогона
недостаточно. Worker ускорил смешанную пару с Dart-отправителем примерно на 9%,
а Dart → Dart — примерно на 1,5%. Малые файлы замедлились примерно на 4%, поэтому
в итоговом коде worker используется только для файлов **больше 1 МиБ**:
один блок не позволяет перекрыть подготовку следующего с отправкой текущего.
100-МиБ путь соответствует измеренному кандидату, 1-МиБ — измеренным контролям.
Общий CI проверил итоговый выбор путей; порог 1,20 не менялся.

Комбинация ускорила Dart → Dart примерно на 5%, Java → Dart на 11%, но не решила
задержку Dart → Java. Только socket 256 КиБ ухудшил последнее направление на 4–5%.
Синхронный controller безопасен для текущего пути и прошёл отдельные pause/cancel/error
тесты, но дал лишь около 2% Dart → Dart; отправка в Java укладывается в колебания
контролей. Эти параметры не включены в приложение. Для локализации оставшейся
разницы снят AOT-профиль отправителя, описанный ниже.

## AOT-профиль Windows

[Диагностика 7502b00](https://github.com/Bel9shik/TransportationFiles/actions/runs/41591110567)
собрала тот же c8ad250 backend через `dart build cli` с native assets и временным
wrapper на публичном [NativeRuntime.streamTimelineTo](https://api.dart.dev/dart-developer/NativeRuntime/streamTimelineTo.html).
Profiler/Perfetto включён только у Dart-отправителя, включая worker isolate.
Пятнадцать измерительных передач после трёх прогревочных в каждом сценарии;
все 1512 полученных файлов независимо проверены. Профилированные времена не
используются как результаты сравнения скорости.

Сохранён только [агрегат](windows-aot-cpu-profile/profile-summary.json): имена
функций/модулей, число samples и безопасные показатели проверки. Raw trace,
адреса, абсолютные пути, память и core не публиковались. Offline parser —
официальный Perfetto 0.59.1. Порядок четырёх профилей подтверждён порядком driver:
100 МиБ Dart → Dart, 100 МиБ Dart → Java, 20 × 1 МиБ Dart → Java, затем Dart → Dart.

В 100-МиБ Dart → Java профиле 428 samples: `_NativeSocket._nativeWrite` — 28%,
`EVP_DigestUpdate` — 19%, чтение файла — 15%, `TransferableTypedData` — 6%,
выделение Uint8Array — 6%. Dart → Dart: 300 samples, запись в сокет — 26%,
SHA — 20%, чтение — 20%, выделение массива — 10%, копирование — 8%.
Это выборки стеков; нативные вызовы могут включать ожидание. Доли не являются
точными CPU cycles и не доказывают, что один участок объясняет всё отставание.
Малые профили (47 и 84 samples) слишком короткие для тонких выводов.
Явного горячего protobuf leaf не обнаружено.

Проверен pinned SDK 3.13.7: Windows
[event handler](https://github.com/dart-lang/sdk/blob/416e33b0ffaef062a60ec966bb8c82ed2b83f128/runtime/bin/eventhandler_win.cc#L685)
жёстко ограничивает одну запись 64 КиБ и допускает одну незавершённую запись.
Копируются только эти 64 КиБ, не весь оставшийся 1-МиБ буфер. После completion
[Dart продолжает исходный буфер с новым offset](https://github.com/dart-lang/sdk/blob/416e33b0ffaef062a60ec966bb8c82ed2b83f128/sdk/lib/_internal/vm/bin/socket_patch.dart#L2654).
Текущая цепочка выдаёт Uint8List с полным backing buffer и не попадает в ветвь
[дополнительного копирования неполного view](https://github.com/dart-lang/sdk/blob/416e33b0ffaef062a60ec966bb8c82ed2b83f128/sdk/lib/io/common.dart#L123).
Публичной настройки размера/числа outstanding writes у Socket/RawSocket нет.
Ранее проверенные SO_SNDBUF/SO_RCVBUF этот механизм не меняют.

## Windows: переиспользование буфера чтения

[Последний контролируемый прогон 0d30403](https://github.com/Bel9shik/TransportationFiles/actions/runs/41593138534)
сравнил c8ad250 с одним повторно используемым 1-МиБ Uint8List в worker через
`readIntoSync`, отдельно и вместе с синхронным upload-controller. SHA обрабатывает
байты до повторного чтения; TransferableTypedData копирует фактический блок,
поэтому выданные блоки сохраняют независимое содержимое. Протокол и лимиты прежние.
Три прогрева + девять измерений, включая смешанные пары. Все 4032 полученных файла
проверены по размеру и SHA-256; analyze, полный набор тестов и отдельные
pause/cancel/error-тесты синхронного controller прошли.
[Сырые данные](windows-reusable-read/).

| Вариант | Java, 100 МиБ | Dart, 100 МиБ | Java → Dart | Dart → Java | Dart, 20 × 1 МиБ |
|---|---:|---:|---:|---:|---:|
| Контроль до | 0,5788 с | 0,5001 с | 0,4840 с | 0,6508 с | 0,1091 с |
| Переиспользование буфера | 0,5440 с | 0,4937 с | 0,4288 с | 0,6342 с | 0,1062 с |
| Буфер + синхронный controller | 0,5511 с | 0,4911 с | 0,4421 с | 0,6326 с | 0,1054 с |
| Контроль после | 0,5422 с | 0,4981 с | 0,4410 с | 0,6324 с | 0,1061 с |

Переиспользование улучшило Dart → Dart лишь на 0,9–1,3%, сочетание — на 1,4–1,8%.
Важное для остаточной задержки направление Dart → Java не быстрее последнего
контроля: 0,6342 / 0,6326 против 0,6324 с. Сравнение только с первым контролем
скрыло бы дрейф runner. Файлы по 1 МиБ worker не используют; при сочетании малый
пакет Dart → Java, наоборот, занял 0,1874 с против 0,1846 / 0,1707 с в контролях.
Практически значимого устойчивого выигрыша отправителя не подтверждено,
оба экспериментальных изменения отклонены. Итоговый код остаётся c8ad250;
Windows +7,8% из полного CI и нестабильный повторный запуск macOS Intel открыты.

## Проверки и воспроизведение

- Локальный `flutter analyze` — без замечаний; 69 тестов прошли, LAN-тест пропущен.
- Стенд совместимости предварительно собирает Java и Dart AOT с native assets,
  чтобы компиляция на чистом CI не расходовала сетевой таймаут.
- Передача Java ↔ Dart прошла в обе стороны: один файл, пакет, пустой файл,
  одинаковые имена и Unicode.
- В более ранней локальной проверке на Android 17 ARM64 эмуляторе с 16-КиБ
  страницами памяти прошли передача через UI, сверка полученного файла, PNG
  в буфере и список файлов. На c8ad250 UI эмулятора повторно не запускался;
  текущий Android release APK успешно собран в CI.
- Отмена отправки закрывает генератор без повторной ошибки в отменённом gRPC-вызове;
  тест проверяет очистку приёмника и освобождение исходного файла.
- Добавлены тесты объединения кредитов, таймера, отмены/обратного давления,
  ошибок и переполнения, а также SHA-256 против независимого Dart-эталона.
- В CI добавлены AOT-замеры на четырёх desktop runner. Порог регрессии — Dart/Java
  не выше 1,20 по медиане обоих сценариев; запас учитывает шум общих runner.
  Результаты сохраняются даже при превышении порога.

С нативными зависимостями нужен CLI-бандл: `dart compile exe` не включает их.

```sh
./gradlew :core:prepareTransferBenchmark
cd flutter_app
dart build cli --target=tool/benchmark.dart --output=build/transfer-benchmark
cd ..
python3 scripts/benchmark_transfer.py \
  --java /path/to/jdk17/bin/java \
  --classpath core/build/benchmark-classpath.txt \
  --dart-aot flutter_app/build/transfer-benchmark/bundle/bin/benchmark \
  --output /tmp/transfer-results.json --max-dart-ratio 1.2
```

`--cross` добавляет Java → Dart и Dart → Java с той же независимой проверкой файлов.

Раздельные пробы SHA-256, диска, flush, protobuf и TCP: `benchmark components`.
Они служат диагностикой; итоговое сравнение выполняет отдельный стенд с SHA-проверкой.

На Windows executable имеет расширение `.exe`; для сборки BoringSSL нужен NASM.
Сборке нужен CMake. На локальном Mac без полного Xcode использовалась временная
обёртка CMake, добавляющая при конфигурации
`-DCMAKE_OSX_SYSROOT_INT=/Library/Developer/CommandLineTools/SDKs/MacOSX.sdk`
и `-DSDK_VERSION=26.5`. Она не меняла SDK, сторонние пакеты или настройки системы.

## Диагностика повторного запуска Mac Intel

В прогоне e5d0926 передача, совместимость Java/Dart, UI и буфер обмена на Intel
прошли. При отдельной проверке упакованного приложения Java запустилась пять раз
(медиана 1,713 с), а Flutter после двух успешных запусков не выдал маркер первого
кадра в третьем запуске за 15 секунд. [Результат](startup-macos-intel-e5d0926.json).
Это отдельный сбой повторного запуска, а не передачи. Таймаут не увеличен;
при следующем воспроизведении стенд сохраняет журнал приложения и снимок
нативных потоков macOS перед завершением зависшего процесса.

Повтор на чистом Intel runner с уже собранным пакетом воспроизвёл завершение
процесса до первого кадра с кодом −4 (`SIGILL`): [диагностика](https://github.com/Bel9shik/TransportationFiles/actions/runs/41448035212).
Причина сигнала пока не установлена; успешные измерения передачи не являются
подтверждением исправности повторного запуска Mac Intel.


Последующие серии на том же образе macOS 15.7.9 / 24G830 и runner image
20260824.0482.1 включали 20 успешных запусков подряд, но отдельный стресс-прогон
снова завис до первого кадра на 12-м запуске. Поэтому серия успехов не закрывает
проблему. В [реальном зависании](https://github.com/Bel9shik/TransportationFiles/actions/runs/41462098319)
сохранён live sample процесса: главный поток находился внутри Flutter/AppKit,
а raster-поток — в подготовке Metal. Символы Flutter/App разрешены не полностью;
это не доказывает причину зависания или отдельного SIGILL. Нативное хеширование
не обнаружено в этих стеках; менять его из-за этого наблюдения оснований нет.
PR остаётся черновиком до подтверждения исправности повторного запуска.


Ограничение стартового маркера: `addPostFrameCallback` фиксирует завершение
framework pipeline и последующую асинхронную запись файла. Это не подтверждение
окончания GPU raster; для него Flutter предоставляет `waitUntilFirstFrameRasterized`.
Сохранённый sample подтверждает живой процесс без стартового маркера за 15 секунд,
но не позволяет объявить GPU причиной зависания. Близкие upstream-исправления
Intel/memmove (#160645) и lifecycle (#188772) уже присутствуют в SDK 3.47.9;
переносить их повторно или отключать renderer на основании этого sample не нужно.
